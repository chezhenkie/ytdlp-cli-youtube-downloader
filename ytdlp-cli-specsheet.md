## 1. Problem, goals, non-goals

Problem: downloading a youtube video with yt-dlp means remembering flags. Users want to paste a url, press enter, and have a download run with sensible saved defaults, changeable without flags.

Goal: a text-menu CLI that owns the menu, the launchers, the defaults and the process plumbing, and delegates every byte of downloading to yt-dlp. Everyday use is: start, paste url, done. Non-affiliation statement is published verbatim in README.md line 1.

Non-goal: this project is not a download engine, a youtube client, or affiliated with or endorsed by the yt-dlp project (README.md line 1). Thumbnail and metadata options were deliberately dropped (CHANGELOG v1.2 "drop the thumbnail and metadata options"), which also removed the last ffprobe consumers; the product tree has no ffprobe (CHANGELOG v1.2 "delete ffprobe.exe"). No macOS ffmpeg bundle: gyan.dev publishes Windows binaries only and no free static macOS build exists (THIRD-PARTY-NOTICES.md lines 37-38; ytdlp.py L380-L386), so macOS gets install instructions (install_ffmpeg L1455-L1459, offer_ffmpeg L1534-L1537).

## 2. Functional requirements

FR-1 Quick download. When a url (any text containing an http(s) substring, cleaned of surrounding punctuation by clean_url, ytdlp.py L692-L696, L316) is entered at the quick-arg path or the main prompt, the system downloads it with saved defaults, per do_download L1562-L1639. Verified by selftest checks on clean_url and argv building (ytdlp.py L2640-L2642, L2449-L2589).

FR-2 Menu surface. Thirteen rows numbered 1 to 13 in one always-visible box (WIDTH 64, ytdlp.py L34; menu_items L1892-L1930): 1 video/audio, 2 format container, 3 video resolution, 4 audio format, 5 output folder, 6 filename template, 7 subtitles, 8 playlist on/off, 9 add multiple youtube urls, 10 reset defaults, 11 update yt-dlp + cli, 12 auto update, 13 quit. Values render per current settings; audio-only greys out container and resolution with "audio only mode has no container" / "...no resolution" refusals (L2225-L2234). Unknown non-url input prints "pick 1-13 or paste a url" (L2348-L2349).

FR-3 Settings persistence. Every menu change writes app-python/config/settings.json immediately, LF line endings, written through a tmp file and os.replace, and skipped entirely when the serialized bytes are unchanged (save_settings L483-L499). Unknown keys in the json are ignored on load (load_settings L473-L475). Quick-run overrides never persist: the url dispatch path (L3268-L3269) runs do_download directly and never calls save_settings.

FR-4 Menu input protocol. The prompt takes a url or a number; "q", "quit", "exit" also quit (L2344); escape at the main prompt wipes results or is a no-op and never exits; EOF and Ctrl+C exit code 0 (L1974-L1982). Escape inside any submenu raises GoBack and repaints the menu once (GoBack L123-L125, handler L1996-L1999). Every submenu message holds on screen behind an unlabelled hold() read so the repaint cannot erase it (hold L1649-L1656; pinned per call site by selftest L2945-L3006).

FR-5 Entry reader. A tty-aware line reader over LineEdit: msvcrt on windows, termios+raw on posix, plain input() when piped (read_esc L233-L314). Up/down arrows recall submitted urls and menu numbers, newest first, down past the newest restores the half-typed draft, left/right and function keys put nothing into the line (LineEdit L131-L187, history capped at 100, HISTORY L127-L128).

FR-6 Output folder. Saved output_dir wins verbatim; else auto-resolve: windows registry Shell Folders Desktop then the Downloads GUID, else XDG user-dirs, then home Desktop then home Downloads, each gated on existing (auto_outdir L544-L576, resolve_outdir L579-L588); last resort "downloads" at the project root. Menu item 5 offers the native folder dialog first (SHBrowseForFolderW via ctypes L2019-L2047, tkinter/zenity/kdialog L2050-L2076), typed path as fallback (L2237-L2247).

FR-7 Download run. When a url is dispatched: scheme gate, then yt-dlp resolution (saved yt_dlp_path, then ROOT/bin, then PATH, L618-L629), then one grouped preflight dot stage that freezes "ready - yt-dlp v<version>, ffmpeg found" or the no-ffmpeg variant (L1574-L1588). The run spawns yt-dlp with stdout/stderr piped, two daemon pump threads, and an escape-only KeyWatch (run_download L1238-L1308). No input is accepted while a download runs; the only interruption is escape. All yt-dlp intermediates (part files, per-chunk fragment files, resume markers, pre-merge files) go to the download work folder inside the output folder; the folder is removed when it ends empty (FR-8, FR-11).

FR-8 Format logic. build_args(s, url, ffdir) with ffdir explicit (L762-L808): audio only with ffmpeg: "-f bestaudio/best -x --audio-format <fmt> --audio-quality 0"; audio only without: "-f bestaudio"; video no audio: "bv*[height<=N]" (bare "bv*" for best); video with ffmpeg: "bv*[height<=N]+ba/b" (bare for best) plus "--merge-output-format <container>" unless container is best; video without ffmpeg: "-f b", single best file. Always: --retries 5, --newline, -o template, -P home:<outdir> and -P temp:<outdir>/.ytdlp-tmp unless the template is absolute, playlist block (--playlist-items 1-<n> when capped, else --no-playlist), --js-runtimes node only when node is on PATH, --ffmpeg-location when ffdir exists. The temp path is the download work folder (TEMP_DIR_NAME .ytdlp-tmp inside the output folder, temp_dir L594-L603): yt-dlp writes every per-chunk fragment file, .part file, .ytdl resume marker and pre-merge file there (pinned source: downloader/fragment.py _download_fragment/_append_fragment in resources/ytdlp-master.zip), so the output folder shows finished files only and the final move is a same-volume rename (movefilesafterdownload.py L50); owner decision 2026-10-14 after the measured flicker: 396 fragment create/delete events in the output folder for one 10-minute HLS download, 1 final-file event with the work folder. Exact selector strings are pinned by selftest (L2449-L2589). Without ffmpeg the CLI says so and degrades rather than failing (stage variants L1583-L1587).

FR-9 Subtitles pass. Subtitles run only after a successful video download, as a separate best-effort yt-dlp pass with --skip-download --write-subs --write-auto-subs --sub-langs <patterns> --no-playlist --newline --convert-subs srt (vtt without ffmpeg), (build_sub_args L811-L824, do_download L1623-L1637). Rationale pinned in code: a rate-limited subtitle api (HTTP 429) must never block the video (L765-L766, L812). Language input maps to patterns so en matches en, en-GB, en-US and en-orig (sub_lang_patterns L707-L719); the 191-code IANA BCP 47 reference set (plus grandfathered in/iw/ji/mo/sh and fil, KNOWN_LANG_CODES L349-L371) validates shaped tokens but never gates: well-formed unknown codes are kept with a note, malformed ones are dropped with a note, and nothing valid left keeps the old value (parse_lang_input L722-L744). Verdict lines build through sub_success_lines(codes) and sub_fail_lines(err) so the parse-miss notes of IF-4 are testable outside a download run.

FR-10 Stage lines. Every progress line rewrites after "\r\x1b[K" so a shorter value never leaves a tail (Stage L1035-L1090). Preflight, ffmpeg offer and subtitle stages use the amber dot stage (dot_stage L843-L849). The download stage picks one of eight random animations per run (comet, pulse, orbit, scanner, twinkle, eq, fill, bounce; pick_spinner L1010-L1012, SPINNERS L997-L1007, ported from scripts-tools/spinner-demo.py, comment L852-L854) and keeps spinning beside yt-dlp's own progress numbers. Progress colors: percent amber 214, size mint 121, speed light blue 117, ETA purple 176, plain words grey 250 (color_progress L97-L120); numbers are width-stable: one decimal truncated (one_dec_num L72-L79) and speed zero-padded to the same ten characters yt-dlp pads (pad_speed L82-L94). A write lock serializes spinner threads against freezes (L1056, L1083-L1086). Verdict freezes: success "downloading - finished" plus a file line; failure "downloading - failed (rc=...): <full yt-dlp error line>" untruncated (fail_sentence L1311-L1316); escape stop "downloading - stopped by escape[, cleaned <n> partial file(s)]" (L1599-L1607).

FR-11 Escape interruption. Escape during a run kills the whole process tree (taskkill /F /T on windows, killpg SIGKILL on posix, _kill_tree L1223-L1235), deletes fresh *.part* and *.ytdl files from the work folder (clean_partials L1163-L1177, called on escape at L1600, mtime after run start with 5 s slack; drop_temp_dir L606-L612 removes the folder when it ends empty), and returns rc 130 which breaks a batch entirely (L1599-L1607, L1743-L1744).

FR-12 Batch downloads. Menu item 9 collects urls one per line with the menu repainting above the input; entries with no http link stay in the list marked "error in url" and are skipped at run time; downloads run strictly sequential in paste order; escape inside any run stops that run and the rest of the batch (multi_url L1749-L1772, run_batch L1718-L1746).

FR-13 Updaters. Menu item 11 runs update_all: yt-dlp updates itself via "<binary> -U" with a pre and post probe_version (update_yt_dlp L2079-L2103), then the CLI self-updates from the raw main-branch source file, fetched in one GET so version and bytes cannot disagree (fetch_cli L2120-L2128, comment L398-L399), gated by compile() and installed via ".new" file plus os.replace, refusing zipapp or frozen installs (install_cli L2131-L2155). Menu item 12 toggles the daily auto-update check, which runs at menu start, stamps settings auto_update_last_check, throttles to one check per 86400 s, only prints what is newer, and asks y/n (enter = no) before touching anything (auto_update_check L2158-L2204, L1971).

SELF-UPDATE, NATIVE IMPLEMENTATION (owner-decided 2026-10-14; the one place where "same as python" is deliberately not literal). A running executable cannot be overwritten on either platform, and `compile()` has no native analogue, so the native install replaces the file and the validity gate is replaced with a stronger one:
  - Resolve the newest release tag, download that tag's asset for the running platform, and verify it against the digest published with it. Version and bytes come from one response, preserving the single-request property of the Python design.
  - Run `<new> --selftest` once before anything is touched. A binary that cannot pass its own checks is never installed.
  - Install by renaming the running binary to `.old` and placing the new one at its path. This is required because a running Windows exe cannot be overwritten and a running ELF yields ETXTBSY on rename; rename-then-place is legal on both and leaves the running process on its own inode. The `.old` file is removed on the next successful start.
  - All of it stays behind the existing y/n prompt, and no existing file is touched until the prompt is answered yes.
  Rationale: the digest-plus-selftest gate is strictly stronger than parse-the-source, and it is the only formulation that works on a compiled artifact. TRIGGER RULE (owner-pinned 2026-10-14, doc only - no behavior change): the check lives at exactly one call site, the top of main_menu, and runs only there and only when stdin is a real console (tty). Quick mode (a url passed as argument), --check, --selftest, CI, and every piped or detached run skip it entirely: no network contact, no settings stamp. There is no resident program and no timer during a session - the check is one-shot at menu open, throttled by the stamp. Consequence for the user: auto-update can only ever be offered while you sit at a console menu you started yourself; if updates seem to not happen, the answer is that no interactive menu was opened - run the program and the check runs with it.

FR-14 ffmpeg fetch offer. On an os with no ffmpeg and a human on the line (stdin tty), the CLI offers the published build - gyan.dev essentials zip on windows, BtbN/FFmpeg-Builds on linux - and installs only after reading the provider's published digest, downloading to a temp path, verifying sha256, lifting the binary from the archive, and probed -version success (retried 3 times), then os.replace into bin/ with chmod 0o755 on posix; checksum mismatch or unrunnable binary changes nothing (install_ffmpeg L1446-L1512, offer_ffmpeg L1515-L1559; order rationale L1447-L1453).

FR-15 Diagnostics. --check prints platform, project root, resolved yt-dlp binary and version, ffmpeg dir or MISSING, output folder and settings file (show_check L2355-L2366). --update is the non-interactive form of item 11 (L3254, L3266-L3267).

## 3. Non-functional requirements

NFR-1 No system runtime. The published artifact must run on a machine with nothing installed beyond its own bundle: no interpreter, no package manager, no redistributable, no toolchain. Two implementations satisfy this differently.
  - Python (shipped through v1.5.0): stdlib only, Python 3, no pip installs (docstring L8); launchers name python/python3 from PATH; CI pins 3.12, workflow L21-L23. Python 3 on PATH is a stated prerequisite of the bundle, documented in README "Requirements".
  - Native (`app-rust/`, planned): one statically self-contained binary per platform. No dependency is acceptable at the user's end, including the Microsoft Visual C++ runtime. `x86_64-pc-windows-msvc` links that runtime dynamically by default and would require vcruntime140.dll on the host, so `.cargo/config.toml` sets `-C target-feature=+crt-static` for that target. Verified: `rustc --print cfg --target x86_64-pc-windows-msvc` reports no crt-static by default and reports `target_feature="crt-static"` with the flag. Omitting it builds cleanly and fails only at the user's machine, so gate G1 asserts the built exe's PE import table contains no vcruntime*.dll and no msvcp*.dll, and gate G10 repeats the assertion against the extracted bundle.
  Build-time dependencies are a separate concern from end-user dependencies and are recorded in section 4; crates are build-time only and ship no runtime requirement.
NFR-2 Machine-agnostic: no hardcoded paths anywhere; bin discovery is settings override, then bin/, then PATH; output resolves per os (FR-6, FR-7). Windows, linux and macOS run in CI (workflow L12-L18); the linux launcher must survive sh/dash via $0, not ${BASH_SOURCE[0]} (CHANGELOG v1.3 "first public release").
NFR-3 Process hygiene: run_download's threads are daemonized, escape kills the tree and cleans partials, the ffmpeg installer removes its temp dir on every path (L1511-L1512), and repeated runs leave no leaked processes, stale files or lingering threads (L1180-L1235). The download work folder is removed whenever it ends empty (drop_temp_dir L606-L612); partials with resume value are never deleted silently.
NFR-4 Testability: every requirement has at least one executable check in every implementation that ships it, and all checks are offline. The Python suite is `--selftest`, 177 checks covering argv building, format branches, playlist/sub guards, color and width rules, spinner shapes, render helpers, outdir resolution, download work folder argv and cleanup (temp path, fresh-partial removal, empty-folder removal), fail_sentence, menu rows, batch order and escape stop, language parsing and layout, hold call sites, checksum parsers, install_cli refusals, extract_member fixtures, the ffmpeg-9 probe shim, the audit regressions (settings boundary coercion, the 6 s auto-check timeout, probe and outdir memos, the single save point, column-width menu truncation), and the parse-miss verdict helpers (live run 2026-10-14: "177 checks, 0 failed"). The native suite carries a Rust twin for each of those 177 checks with the same expected output, plus the NFR-1 import-table assertions. Two acceptance rules apply to the port:
  - Differential, not reimplemented. The native suite must assert the same expected values as the Python suite for the same inputs. A check that merely re-expresses the implementation's own output proves nothing and is not accepted as a twin.
  - The instrument is proven before it judges. The differential harness must pass against a known answer produced by the Python implementation before it is used to evaluate any native code.
  The count 169 describes the Python suite and is not a target for the native suite; the native suite's own count is whatever its 177 twins plus the import-table assertions come to, and is recorded when it exists rather than predicted here. CI runs selftest then --check on all three os (workflow L24-L27).
NFR-5 Privileged controls. Authentication and authorization do not apply (single-user local tool). Enforced locally: input validation at url scheme gate L1563-L1565 and argparse choices L3245-L3247; secrets: settings.json ships no machine paths, repo carries no binaries (bin/ and releases/ gitignored, .gitignore); integrity: every downloaded binary is digest-verified before installation (FR-13, FR-14); logging: stage lines are the whole observable log and stdout/stderr tails keep the last 6 error lines (L1272-L1277); retention: only user-chosen paths in the user's own settings.
NFR-6 ASCII-only source and console safety: ascii_safe maps unicode punctuation and encodes the rest with replace so windows cp1252 cannot crash output (ascii_safe L1093-L1102).
NFR-7 Outside a tty the CLI renders plain: no colors, stages skip the spinner thread and only the final line prints (c() L62-L70, USE_COLOR L44, Stage.start L1058-L1061).
NFR-8 Licensing compliance as a design property: MIT CLI (LICENSE), Unlicense yt-dlp, GPL-2.0-or-later ffmpeg shipped only in portable bundles with GPL-2.0.txt and GPL-3.0.txt inside and THIRD-PARTY-NOTICES.md naming the exact archive and digest per platform (THIRD-PARTY-NOTICES.md lines 8-46); nothing in the bundle restricts GPL rights for ffmpeg (lines 47-51). Binaries are never in git.

## 4. Architecture

Two implementations share one behaviour specification. Both are held to the functional requirements above without exception; the port changes the implementation, not the product.

PYTHON (shipped, authoritative through cutover). Single module src/ytdlp.py (123121 bytes, 3274 lines (newline count), sha256 98818B510A182094E30524CC0218300CDC38FFA08137B22537FF4B416F0728AA at the v1.5.0 release commit). Layers by responsibility: terminal plumbing (colors, c(), read_esc/LineEdit, Stage, KeyWatch), configuration (DEFAULTS, load/save), resolution (find_yt_dlp, find_ffmpeg_dir, auto_outdir, temp_dir, drop_temp_dir), argument construction (build_args, build_sub_args, output_args), process execution (run_download, probe_version, kill/clean), update machinery (update_yt_dlp, fetch_cli, install_cli, install_ffmpeg, offer_ffmpeg), and UI (menu_items, render, act, submenus, selftest). It imports stdlib only, including math and random (L27-L29).

NATIVE (`app-rust/`, planned). One binary per platform, split into modules along the same seven layers. Single-module is not carried over: the module count is an implementation detail of the port, and the layer boundaries are the constraint that matters (owner decision, F9 stays closed for Python only). Capability-by-capability, because Python's stdlib supplies things Rust's does not:

| capability | Python source | Rust std | native choice |
|---|---|---|---|
| raw keys, echo, kbhit | msvcrt / termios | none | FFI: windows-sys, libc |
| VT enable | ctypes kernel32 | none | FFI: windows-sys |
| shell folders | winreg | none | FFI: windows-sys |
| folder dialog | SHBrowseForFolderW via ctypes | none | FFI: windows-sys; posix shell-out unchanged |
| terminal size | os.get_terminal_size | none | FFI: windows-sys GetConsoleScreenBufferInfoW; libc TIOCGWINSZ; any error reads as no room (block_under_input) |
| process tree kill | taskkill /F /T | spawn | unchanged |
| sha256 | hashlib | none | hand-rolled, streaming, NIST vectors pinned |
| json | json | none | hand-rolled for the 16-field schema |
| rng | random | none | hand-rolled PCG32 |
| east-asian width | unicodedata | none | hand-rolled pinned table |
| http + tls | urllib.request | none | ureq + rustls + webpki-roots |
| zip | zipfile | none | zip |
| tar.xz | tarfile | none | xz2 + tar |
| charset safety | fixed map + ascii replace (ascii_safe) | per-site (see language rules) | hand-rolled 9-pair map + ascii replace; decode policy per site |

Crate policy (owner decision): minimal vetted set. A crate is permitted only where std genuinely lacks the capability and hand-rolling would be a security liability - TLS and HTTP being the clear case. sha256, JSON, the RNG and the east-asian width table are hand-rolled because they are small, auditable and testable offline. No TUI crate and no terminal framework: the menu stays a hand-rolled ANSI box over the existing reader, per the owner's no-special-frontend rule.

Language-specific rules that are gates rather than style, recorded so they are auditable: writers are wrapped in a BufWriter once outside every loop with an explicit flush before drop and write_all, because Rust File is unbuffered where Python's was not - bulk paths only: interactive stdout is locked per frame and flushed after every frame and before every blocking read, matching the 16 flush sites the Python calls explicitly; hot loops allocate no format! / clone / to_string per iteration and reserve known sizes; the release profile sets overflow-checks = true so a ported arbitrary-precision assumption panics instead of silently wrapping; decoding is explicit at every byte boundary, per site (the download and http pipes decode UTF-8 with replacement; subprocess helper reads use the locale encoding as Python text=True does; settings reads are strict UTF-8 into the settings-unreadable branch), and no byte-offset slicing assumes ASCII; no bare unwrap, every former exception path is a tested Result branch. Rationale and sources: python-to-rust-refactor-pitfalls.md.

NATIVE PORT NOTES recorded during phase 2, so they are auditable decisions rather than implicit drift: integers are i64 throughout - a settings value or version piece beyond it saturates at the i64 bound instead of python's arbitrary precision (no real yt-dlp or youtube value approaches that, and the differential protocol itself carries i64 only; pinned by rust tests); numeric pattern matching over yt-dlp or user input is ASCII (the unicode `\d`/`isdigit()` forms are not ported - yt-dlp emits ASCII digits, and the harness protocol cannot carry the rest); `pick_checksum` splits checksum files on `\n` (python `splitlines` also splits rarer separators; the published files are LF/CRLF); float rendering reproduces CPython `repr` semantics (`py_float_repr`, pinned against CPython values) because the coercion path calls `str()` and the settings writer will need the same rendering.

NATIVE PORT NOTES recorded during phase 3 (state layer), so they are auditable decisions rather than implicit drift: the settings-file codec reproduces CPython `json` as the settings file sees it - floats parse as floats, `NaN`/`Infinity`/`-Infinity` parse as non-finite floats and are written back with those exact spellings while finite floats keep `repr` semantics through `py_float_repr`; the writer emits `json.dumps(s, indent=2, sort_keys=True)` plus one LF with `ensure_ascii=True` escaping (short forms and `\uXXXX` for 0x00-0x1f, `\uXXXX` for 0x7f and every char above, astral chars as surrogate pairs); integers saturate at i64 as everywhere in the port, so a bignum in a settings file is the one divergence the differential protocol cannot carry - pinned by rust tests instead; duplicate keys are last-wins like a python dict; a lone-surrogate `\u` escape (unrepresentable in a rust String) maps to U+FFFD, recorded - python keeps the lone surrogate; the read path applies python's universal-newline translation (CRLF and lone CR to LF) for both the load parse and the `save_settings` skip-compare, so a CRLF file equal to the LF render is skipped exactly like python, and the loader never writes; a settings file whose JSON is not an object is where python raises outside its `try` - the port carries those as typed error branches and the harness compares port-domain shape tokens (`unreadable`, `type_error`, `attribute_error`, `not_utf8`) because payloads are shape-gated per the message rule above; `not_utf8` is the invalid-UTF-8 case where python raises `UnicodeDecodeError` in the save compare, while every other read failure falls through to the write like python's `except OSError`. Harness vector inputs may carry JSON floats and the `NaN`/`Infinity` literals for the settings-writer cases; the interchange records stay i64-only.

NATIVE PORT NOTES recorded during phase 4 (resolution and diagnostics), so they are auditable decisions rather than implicit drift: every process-state read (which answers, PATH and PATHEXT values, shell-folder registry values, home, the environment map, file mtimes, subprocess outcomes) is a parameter of the ported function, with the real lookups in the same module, so the differential runs both sides against identical injected state in private scratch dirs and path-carrying records project each side's scratch prefix as `{scratch}`; `shutil.which` is ported for the fixed query names this product uses (`yt-dlp`, `yt-dlp.exe`, `ffmpeg`, `node`) - posix PATH scan with a real `access(2)` X_OK check through libc and the isdir exclusion, windows with the PATHEXT machinery, the pinned default list `.COM;.EXE;.BAT;.CMD;.VBS;.JS;.WS;.MSC`, the extension-suffix direct-match rule and the curdir candidate as the literal `.`; the `_winapi.NeedCurrentDirectoryForExePath` refinement is not ported because it only changes the answer for system-executable names, which none of the four fixed names is; PATH is decoded as UTF-8 and non-UTF-8 PATH entries are a recorded deviation; `os.access(X_OK)` is the real `access(2)` on posix and existence on windows (measured 2026-10-15: X_OK is true for any existing path including directories; the isdir exclusion is the shutil helper, as in python); the pathlib 3.14 lexical model is ported as `path_render`/`path_is_absolute`/`splitroot` (altsep folding, splitroot, the UNC drive/root post-processing for `//server/share` forms, empty and `.` components dropped, the `.` render fallback) and its behaviour is pinned against probed oracle matrices on both OSes rather than inferred from source, because the 3.14 parsers are C builtins; `Path.is_absolute` is `ntpath.isabs` of the rendered string on windows and the raw string's leading `/` on posix, exactly as pathlib 3.14 does, and this is the rule the port uses for the saved-folder and saved-binary strings too - `find_yt_dlp`/`find_ffmpeg_dir` build every candidate as a rendered string; the saved-path and output-dir values carry python's crash shapes as typed branches (truthy non-string `yt_dlp_path`/`ffmpeg_path` is python's `TypeError` at `Path()`, truthy non-string `output_dir` is the `AttributeError` at `.strip()`; both are reachable through `--check` because `coerce_settings` does not touch those keys); `expandvars` is ported from the probed oracle matrices for both spellings (`$name`, `${name}`; plus `%name%` and the single-quoted-chunk skip on windows only; single pass; `$$` collapses only on windows, `%%` to `%` only on windows, unknown names stay verbatim, windows lookups compare by unicode `str.upper`), and `~` expansion resolves HOME on posix and USERPROFILE else HOMEDRIVE+HOMEPATH on windows - the passwd-database and `~user` fallbacks are not ported (recorded deviation; ## 5. Interfaces

IF-1 Launcher contracts. Two sets, one per implementation; both forward arguments unchanged and neither adds or drops one.
  - Python: run-ytdlp.bat resolves %~dp0src\ytdlp.py, forwards %*, pauses on nonzero exit (L1-L5). run-ytdlp.sh resolves its own dir via cd+pwd on $0, prefers python3 then python, forwards "$@" (L1-L5), posix-safe under sh via no bashisms in the arguments it builds.
  - Native: the launcher becomes thin and the contract moves to the executable itself. run-ytdlp.sh resolves its own directory the same $0 way and execs the binary beside it, keeping the dash-safe property; run-ytdlp.bat execs the exe beside it and keeps the nonzero-exit pause. The "pause on nonzero exit" behaviour is preserved because a double-click has no console to show an error in. The project-root resolution that Python gets from `Path(__file__).resolve().parent.parent` is reproduced natively from the executable's own path, so bin/, config/ and downloads/ keep the same meaning and the product stays machine-agnostic (NFR-2).

IF-2 CLI argv. Positional url plus one-shot overrides: -a/--audio, -f/--format (mp4 mkv webm best), -r/--resolution (2160..360 best), --af (mp3 m4a opus wav best), -o/--outdir, --template, --subs, --playlist, and mode flags --menu, --check, --update, --selftest (argparse L3242-L3255). Overrides mutate the in-memory settings only (apply_overrides L3222-L3238). The flag set, the accepted values, the help text and the rejection behaviour are part of the product contract and are identical in both implementations; only the parser is native in the port, and the accepted-value lists stay the single source of truth for both (FR-8).

IF-3 settings.json schema. Serialized defaults, written by the product only (FR-3). Fields in the Data section.

IF-4 yt-dlp subprocess. argv per FR-8 and FR-9 with "--newline" for line-pumpable progress; stdout parsed for "[download]" progress lines, "Writing video subtitles to:" language extraction, "Destination:" suppression; stderr keeps a 6-line error tail (run_download L1252-L1280). Compatibility depends on these shapes; the pinned yt-dlp source is the reference (resources/yt-dlp-master.zip). PARSE-MISS POLICY (owner-approved 2026-10-14, audit F11 softened into detection instead of a json contract): the stdout scraping stays, but a silent degrade becomes a spoken miss. A subtitle pass that exits 0 with no language codes read prints its verdict plus one amber note line ("yt-dlp reported success but no subtitle files were read - wording may have changed, please report"); a subtitle failure whose error line matches no sub_fail_reason pattern prints the not-fetched verdict plus one amber note line ("yt-dlp wording not recognized - please report"). Progress coloring misses nothing verifiable and stays silent. The full uncut error line on any failed download is unchanged. Purpose: yt-dlp upstream rewording its human output surfaces on the user's screen the moment it happens, so the wrapper can be updated to the new wording in the next pass.

IF-5 ffmpeg subprocess. probe_version asks "--version" then "-version" on both stdout and stderr and takes the first rc 0 non-empty line, because ffmpeg 9 rejects the double-dash spelling and answers only "-version" on stderr (probe_version L653-L687; ffmpeg 9 selftest shim L2769-L2797). Called for yt-dlp pre-checks (both binaries) and the freshly downloaded ffmpeg before it replaces anything (FR-14 step 6).

IF-6 Os folder providers. Windows registry Shell Folders (HKCU, expandvars) L506-L520; POSIX XDG user-dirs L527-L538; folder dialogs per FR-6.

IF-7 Network endpoints. CLI self-update fetches the raw main-branch ytdlp.py (one GET, CLI_UPDATE_URL L400-L401); yt-dlp updates via its own -U; ffmpeg provider urls and their published digests are pinned in FFMPEG_SOURCES L387-L395 with digest sources consulted first (FR-14); timeouts: 60 s for forced text fetches, 6 s for the non-forced daily auto-update check (owner-pinned 2026-10-14, audit F3), 1800 s for binary download (DL_TIMEOUT L404, http_text L1365-L1368). All non-forced network touches require either the menu (user action) or auto_update on plus a tty; a failed network contact is silent except when forced (L2174-L2179).

  Native implementation: the first endpoint is replaced per FR-13 (release tag, asset, published digest) and every other endpoint, its timeout and its silence rule are unchanged. The 6 s non-forced timeout is load-bearing rather than incidental - a black-holed network would otherwise stall the first keystroke - so it is pinned by a test in both suites. TLS is provided by rustls with webpki-roots; certificate verification is not made optional. Root certificates are bundled rather than read from the OS trust store, so the binary's behaviour does not vary with the host's certificate configuration.

IF-8 CI and selftest (IF to developers): offline; every push and pull request runs selftest + --check on windows/ubuntu/macos (workflow L1-L28). The native port adds a second workflow covering fmt, clippy with warnings denied, unit tests and a cross-implementation differential check on the same three OS; neither workflow contacts the network in a test (NFR-4).

## 6. Functionality

Startup journey: enable ANSI/VT where needed (L47-L59), paint menu box (header "yt-dlp cli  v1.5.0" centered, blank row, 13 rows, "press escape to exit submenu", rules, L1872-L1945), print the hint block above the input line - verbatim, amber then grey then divider (hint L1856-L1869):

    paste url, press enter and download will start.
    enter number to change default settings
    change download location by choosing menu item: 5
    download several urls at once by choosing menu item: 9
    DL location: <resolved folder>

then auto-update check (FR-13) and first save (L1968-L1972). The menu never disappears: everything paints under it, nothing prints beyond the hint block, item-9 entry lines, and stage/verdict lines (main_menu loop L1954-L2005).

Primary flow (single url): prompt accepts text; first http(s) substring is the url (before any number is consulted, L1984-L1997) - when no url is present, text goes to act(); do_download per FR-7: preflight freeze, then the spinner stage with live progress, then exactly one of three justified verdicts: finished (plus "... <name> (<MB>)" file line via newest_since, 2 s slack, L1146-L1160), failed (full error line), or stopped-by-escape (partial cleanup count). States covered: not a url (message), yt-dlp missing (guidance), yt-dlp fails its check (frozen rc), no ffmpeg (offer per FR-14 or declined continuation), success, failure (always ends in a readable frozen line), escape (kill + clean). Stage lines persist until the next url, menu pick, repaint or escape (L1954-L2005 management of results/dirty).

Batch flow (item 9): FR-12 above; states: empty entry closes and starts, escape returns without downloads, bad line marked and skipped, per-url header line, batch aborted by escape only.

Updaters (items 11/12): FR-13; states: current version ("already current"), newer version offered with enter = no, network down (silent or, when forced, one explanatory line), older published file (no version found message when forced).

Settings flows (items) each end in: new value shown, a hold read, menu repaint; item 10 restores DEFAULTS and answers "defaults restored" (L2329-L2333); item 13 saves and prints the settings path (L2344-L2347).

Failure handling pattern: every detectable failure (missing binary, failed probe, refused install, checksum mismatch, unreadable archive, network loss) ends in a specific user-visible line describing the fix or the kept state; nothing fails silently except non-forced network contact (NFR, L2174-L2179).
