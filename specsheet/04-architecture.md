## 4. Architecture

Two implementations share one behaviour specification. Both are held to the functional requirements above without exception; the port changes the implementation, not the product.

PYTHON (shipped, authoritative through cutover). Single module src/ytdlp.py (123121 bytes, 3274 lines (newline count), sha256 98818B510A182094E30524CC0218300CDC38FFA08137B22537FF4B416F0728AA at the v1.5.0 release commit). Layers by responsibility: terminal plumbing (colors, c(), read_esc/LineEdit, Stage, KeyWatch), configuration (DEFAULTS, load/save), resolution (find_yt_dlp, find_ffmpeg_dir, auto_outdir, temp_dir, drop_temp_dir), argument construction (build_args, build_sub_args, output_args), process execution (run_download, probe_version, kill/clean), update machinery (update_yt_dlp, fetch_cli, install_cli, install_ffmpeg, offer_ffmpeg), and UI (menu_items, render, act, submenus, selftest). It imports stdlib only, including math and random (L27-L29).

NATIVE (`app-rust/`, planned). One binary per platform, split into modules along the same seven layers. Single-module is not carried over: the module count is an implementation detail of the port, and the layer boundaries are the constraint that matters (owner decision, F9 stays closed for Python only). Capability-by-capability, because Python's stdlib supplies things Rust's does not:

| capability | Python source | Rust std | native choice |
|---|---|---|---|
| raw keys, echo, kbhit | msvcrt / termios | none | FFI: windows-sys, libc |
| VT enable | ctypes kernel32 | none | FFI: windows-sys |
| shell folders | winreg | none | FFI: windows-sys |
| folder dialog | SHBrowseForFolderW via ctypes | none | FFI: windows-sys; posix shell-out unchanged |
| terminal size | os.get_terminal_size | none | FFI: windows-sys GetConsoleScreenBufferInfoW; libc TIOCGWINSZ; any error reads as no room (block_under_input) |
| process tree kill | taskkill /F /T | spawn | unchanged |
| sha256 | hashlib | none | hand-rolled, streaming, NIST vectors pinned |
| json | json | none | hand-rolled for the 16-field schema |
| rng | random | none | hand-rolled PCG32 |
| east-asian width | unicodedata | none | hand-rolled pinned table |
| http + tls | urllib.request | none | ureq + rustls + webpki-roots |
| zip | zipfile | none | zip |
| tar.xz | tarfile | none | xz2 + tar |
| charset safety | fixed map + ascii replace (ascii_safe) | per-site (see language rules) | hand-rolled 9-pair map + ascii replace; decode policy per site |

Crate policy (owner decision): minimal vetted set. A crate is permitted only where std genuinely lacks the capability and hand-rolling would be a security liability - TLS and HTTP being the clear case. sha256, JSON, the RNG and the east-asian width table are hand-rolled because they are small, auditable and testable offline. No TUI crate and no terminal framework: the menu stays a hand-rolled ANSI box over the existing reader, per the owner's no-special-frontend rule.

Language-specific rules that are gates rather than style, recorded so they are auditable: writers are wrapped in a BufWriter once outside every loop with an explicit flush before drop and write_all, because Rust File is unbuffered where Python's was not - bulk paths only: interactive stdout is locked per frame and flushed after every frame and before every blocking read, matching the 16 flush sites the Python calls explicitly; hot loops allocate no format! / clone / to_string per iteration and reserve known sizes; the release profile sets overflow-checks = true so a ported arbitrary-precision assumption panics instead of silently wrapping; decoding is explicit at every byte boundary, per site (the download and http pipes decode UTF-8 with replacement; subprocess helper reads use the locale encoding as Python text=True does; settings reads are strict UTF-8 into the settings-unreadable branch), and no byte-offset slicing assumes ASCII; no bare unwrap, every former exception path is a tested Result branch. Rationale and sources: python-to-rust-refactor-pitfalls.md.

NATIVE PORT NOTES recorded during phase 2, so they are auditable decisions rather than implicit drift: integers are i64 throughout - a settings value or version piece beyond it saturates at the i64 bound instead of python's arbitrary precision (no real yt-dlp or youtube value approaches that, and the differential protocol itself carries i64 only; pinned by rust tests); numeric pattern matching over yt-dlp or user input is ASCII (the unicode `\d`/`isdigit()` forms are not ported - yt-dlp emits ASCII digits, and the harness protocol cannot carry the rest); `pick_checksum` splits checksum files on `\n` (python `splitlines` also splits rarer separators; the published files are LF/CRLF); float rendering reproduces CPython `repr` semantics (`py_float_repr`, pinned against CPython values) because the coercion path calls `str()` and the settings writer will need the same rendering.

NATIVE PORT NOTES recorded during phase 3 (state layer), so they are auditable decisions rather than implicit drift: the settings-file codec reproduces CPython `json` as the settings file sees it - floats parse as floats, `NaN`/`Infinity`/`-Infinity` parse as non-finite floats and are written back with those exact spellings while finite floats keep `repr` semantics through `py_float_repr`; the writer emits `json.dumps(s, indent=2, sort_keys=True)` plus one LF with `ensure_ascii=True` escaping (short forms and `\uXXXX` for 0x00-0x1f, `\uXXXX` for 0x7f and every char above, astral chars as surrogate pairs); integers saturate at i64 as everywhere in the port, so a bignum in a settings file is the one divergence the differential protocol cannot carry - pinned by rust tests instead; duplicate keys are last-wins like a python dict; a lone-surrogate `\u` escape (unrepresentable in a rust String) maps to U+FFFD, recorded - python keeps the lone surrogate; the read path applies python's universal-newline translation (CRLF and lone CR to LF) for both the load parse and the `save_settings` skip-compare, so a CRLF file equal to the LF render is skipped exactly like python, and the loader never writes; a settings file whose JSON is not an object is where python raises outside its `try` - the port carries those as typed error branches and the harness compares port-domain shape tokens (`unreadable`, `type_error`, `attribute_error`, `not_utf8`) because payloads are shape-gated per the message rule above; `not_utf8` is the invalid-UTF-8 case where python raises `UnicodeDecodeError` in the save compare, while every other read failure falls through to the write like python's `except OSError`. Harness vector inputs may carry JSON floats and the `NaN`/`Infinity` literals for the settings-writer cases; the interchange records stay i64-only.

NATIVE PORT NOTES recorded during phase 4 (resolution and diagnostics), so they are auditable decisions rather than implicit drift: every process-state read (which answers, PATH and PATHEXT values, shell-folder registry values, home, the environment map, file mtimes, subprocess outcomes) is a parameter of the ported function, with the real lookups in the same module, so the differential runs both sides against identical injected state in private scratch dirs and path-carrying records project each side's scratch prefix as `{scratch}`; `shutil.which` is ported for the fixed query names this product uses (`yt-dlp`, `yt-dlp.exe`, `ffmpeg`, `node`) - posix PATH scan with a real `access(2)` X_OK check through libc and the isdir exclusion, windows with the PATHEXT machinery, the pinned default list `.COM;.EXE;.BAT;.CMD;.VBS;.JS;.WS;.MSC`, the extension-suffix direct-match rule and the curdir candidate as the literal `.`; the `_winapi.NeedCurrentDirectoryForExePath` refinement is not ported because it only changes the answer for system-executable names, which none of the four fixed names is; PATH is decoded as UTF-8 and non-UTF-8 PATH entries are a recorded deviation; `os.access(X_OK)` is the real `access(2)` on posix and existence on windows (measured 2026-10-15: X_OK is true for any existing path including directories; the isdir exclusion is the shutil helper, as in python); the pathlib 3.14 lexical model is ported as `path_render`/`path_is_absolute`/`splitroot` (altsep folding, splitroot, the UNC drive/root post-processing for `//server/share` forms, empty and `.` components dropped, the `.` render fallback) and its behaviour is pinned against probed oracle matrices on both OSes rather than inferred from source, because the 3.14 parsers are C builtins; `Path.is_absolute` is `ntpath.isabs` of the rendered string on windows and the raw string's leading `/` on posix, exactly as pathlib 3.14 does, and this is the rule the port uses for the saved-folder and saved-binary strings too - `find_yt_dlp`/`find_ffmpeg_dir` build every candidate as a rendered string; the saved-path and output-dir values carry python's crash shapes as typed branches (truthy non-string `yt_dlp_path`/`ffmpeg_path` is python's `TypeError` at `Path()`, truthy non-string `output_dir` is the `AttributeError` at `.strip()`; both are reachable through `--check` because `coerce_settings` does not touch those keys); `expandvars` is ported from the probed oracle matrices for both spellings (`$name`, `${name}`; plus `%name%` and the single-quoted-chunk skip on windows only; single pass; `$$` collapses only on windows, `%%` to `%` only on windows, unknown names stay verbatim, windows lookups compare by unicode `str.upper`), and `~` expansion resolves HOME on posix and USERPROFILE else HOMEDRIVE+HOMEPATH on windows - the passwd-database and `~user` fallbacks are not ported (recorded deviation; HOME/USERPROFILE are set in every context the product ships in); `probe_version` takes the subprocess outcome through a spawn callback and the mtime through a parameter with the memo key `(path string, mtime seconds as float)` matching `(str(binary), os.path.getmtime(binary))` including the `OSError`-to-`None` key, successful answers memoized per key and failures never memoized (F4, pinned by named rust tests); the version line uses python `str.strip`/`str.splitlines` semantics in full (the whitespace set includes `\x1c`-`\x1f`, `\x85` and `\xa0`; the splitlines break set beyond `\n` is ported); a spawn failure or timeout surfaces as the shape-gated `error: ` branch (payload recorded, not compared) and the real spawn kills the child at the 60 s timeout; subprocess reads decode UTF-8 (locale is UTF-8 on the differential systems; non-UTF-8 tool output would take the error branch - recorded deviation); `auto_outdir` keeps its process memo as an explicit cache object and the F6 regression is a named rust test counting lookups across calls; the XDG parse reproduces `re.search(r'^\s*KEY\s*=\s*"([^"]*)"', re.M)` semantics (leading `\s*` runs across lines, `^` anchors after `\n` only, the value is `[^"]*`); a user-dirs file that is not valid UTF-8 is python's `UnicodeDecodeError` out of the XDG load and the port carries it as the `not_utf8` shape branch; the injected environment map preserves insertion order so the windows case-insensitive lookups reproduce `os.environ`'s last-assignment-wins; the windows `expandvars` flavor is compiled on every os and pinned by its own probed-matrix rust tests; `auto_outdir`'s registry candidates pass through the same expandvars the python `_win_shell_folder` applies; `show_check` is composed over the injected world and its differential record is the exact stdout text plus the probe and which call paths, with python's `True`/`False` rendering for the `exists=` field; the real `--check` prints python-style line endings (CRLF on windows redirected stdout, measured 2026-10-15; LF elsewhere) and wires the first main() path, with project root = the executable's parent directory (IF-1) and config/bin under it; the shell-folders registry read is windows-sys FFI (0.61.2, `Win32_System_Registry`, the first external dependency of the workspace, drawn from the crate-policy table above); the G4 byte-compare stages each release binary beside a config/bin tree (the repository's `app-python/` in CI) so both implementations resolve the same root by their own rules.

Build matrix. One target per published platform, no fallback target: a broken build fails CI rather than producing a different binary. Linux builds in WSL on this machine; Windows builds in GitHub Actions because the Windows SDK import libraries are absent locally and `lld-link` cannot substitute for them - the compiler is not the missing piece, the SDK is; macOS is CI-only with no published bundle. The Windows build uses host target x86_64-pc-windows-msvc with the NFR-1 crt-static flag.

Data ownership: settings.json is the single source of truth for user defaults; the product owns it exclusively. Known language codes are a pinned source reference, not a setting (L349-L371). All 16 schema fields, types, defaults, validation and code sites are listed in the Data section.

Third-party and licensing: the CLI invokes yt-dlp and ffmpeg as separate processes. This is aggregation per the FSF GPL FAQ, so the MIT CLI and the GPL-2.0-or-later ffmpeg binaries in the portable bundles keep separate licenses (THIRD-PARTY-NOTICES.md lines 4-25). ffmpeg versions shipped: windows gyan.dev 9.0.2 essentials (sha256 60f467265b1e312373dbcd92200c2618a74850f98d3d078e94296bb3fa2047ba), linux BtbN n9.0.2-27-g7e93014c5b-20261013 (sha256 afa2b69c9965919e0b519a633520321f838d74690f8fb28c76393c54a9448d60) (lines 32-44). The pinned yt-dlp source shows yt-dlp itself does not bundle ffmpeg and writes its own speed fields as >10s (bundled reference read 2026-10-13, cited in change history for the width rules).

Alternatives and decisions (record): console background control was tried and reverted by user call (CHANGELOG v1.2 "navy background reverted"); console resize was implemented and reverted (v1.1); the old single-stage download line was replaced by the stage/spinner design (v1.2 "staged download flow"); subtitle work moved from the video run to a separate pass after 429 aborts killed downloads (FR-9 rationale); ffprobe was deleted after its last consumers were removed (non-goals); the release bundles ship one tag with four assets rather than per-platform releases (README asset table).
