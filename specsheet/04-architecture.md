## 4. Architecture

Two implementations share one behaviour specification. Both are held to the functional requirements above without exception; the port changes the implementation, not the product.

PYTHON (shipped, authoritative through cutover). Single module src/ytdlp.py (123121 bytes, 3274 lines (newline count), sha256 98818B510A182094E30524CC0218300CDC38FFA08137B22537FF4B416F0728AA at the v1.5.0 release commit). Layers by responsibility: terminal plumbing (colors, c(), read_esc/LineEdit, Stage, KeyWatch), configuration (DEFAULTS, load/save), resolution (find_yt_dlp, find_ffmpeg_dir, auto_outdir, temp_dir, drop_temp_dir), argument construction (build_args, build_sub_args, output_args), process execution (run_download, probe_version, kill/clean), update machinery (update_yt_dlp, fetch_cli, install_cli, install_ffmpeg, offer_ffmpeg), and UI (menu_items, render, act, submenus, selftest). It imports stdlib only, including math and random (L27-L29).

NATIVE (`app-rust/`, planned). One binary per platform, split into modules along the same seven layers. Single-module is not carried over: the module count is an implementation detail of the port, and the layer boundaries are the constraint that matters (owner decision, F9 stays closed for Python only). Capability-by-capability, because Python's stdlib supplies things Rust's does not:

| capability | Python source | Rust std | native choice |
|---|---|---|---|
| raw keys, echo, kbhit | msvcrt / termios | none | FFI: windows-sys, libc |
| VT enable | ctypes kernel32 | none | FFI: windows-sys |
| shell folders | winreg | none | FFI: windows-sys |
| folder dialog | SHBrowseForFolderW via ctypes | none | FFI: windows-sys; posix shell-out unchanged |
| terminal size | os.get_terminal_size | none | FFI: windows-sys GetConsoleScreenBufferInfoW; libc TIOCGWINSZ; any error reads as no room (block_under_input) |
| process tree kill | taskkill /F /T | spawn | unchanged |
| sha256 | hashlib | none | hand-rolled, streaming, NIST vectors pinned |
| json | json | none | hand-rolled for the 16-field schema |
| rng | random | none | hand-rolled PCG32 |
| east-asian width | unicodedata | none | hand-rolled pinned table |
| http + tls | urllib.request | none | ureq + rustls + webpki-roots |
| zip | zipfile | none | zip |
| tar.xz | tarfile | none | xz2 + tar |
| charset safety | fixed map + ascii replace (ascii_safe) | per-site (see language rules) | hand-rolled 9-pair map + ascii replace; decode policy per site |

Crate policy (owner decision): minimal vetted set. A crate is permitted only where std genuinely lacks the capability and hand-rolling would be a security liability - TLS and HTTP being the clear case. sha256, JSON, the RNG and the east-asian width table are hand-rolled because they are small, auditable and testable offline. No TUI crate and no terminal framework: the menu stays a hand-rolled ANSI box over the existing reader, per the owner's no-special-frontend rule.

Language-specific rules that are gates rather than style, recorded so they are auditable: writers are wrapped in a BufWriter once outside every loop with an explicit flush before drop and write_all, because Rust File is unbuffered where Python's was not - bulk paths only: interactive stdout is locked per frame and flushed after every frame and before every blocking read, matching the 16 flush sites the Python calls explicitly; hot loops allocate no format! / clone / to_string per iteration and reserve known sizes; the release profile sets overflow-checks = true so a ported arbitrary-precision assumption panics instead of silently wrapping; decoding is explicit at every byte boundary, per site (the download and http pipes decode UTF-8 with replacement; subprocess helper reads use the locale encoding as Python text=True does; settings reads are strict UTF-8 into the settings-unreadable branch), and no byte-offset slicing assumes ASCII; no bare unwrap, every former exception path is a tested Result branch. Rationale and sources: python-to-rust-refactor-pitfalls.md.

NATIVE PORT NOTES recorded during phase 2, so they are auditable decisions rather than implicit drift: integers are i64 throughout - a settings value or version piece beyond it saturates at the i64 bound instead of python's arbitrary precision (no real yt-dlp or youtube value approaches that, and the differential protocol itself carries i64 only; pinned by rust tests); numeric pattern matching over yt-dlp or user input is ASCII (the unicode `\d`/`isdigit()` forms are not ported - yt-dlp emits ASCII digits, and the harness protocol cannot carry the rest); `pick_checksum` splits checksum files on `\n` (python `splitlines` also splits rarer separators; the published files are LF/CRLF); float rendering reproduces CPython `repr` semantics (`py_float_repr`, pinned against CPython values) because the coercion path calls `str()` and the settings writer will need the same rendering.

NATIVE PORT NOTES recorded during phase 3 (state layer), so they are auditable decisions rather than implicit drift: the settings-file codec reproduces CPython `json` as the settings file sees it - floats parse as floats, `NaN`/`Infinity`/`-Infinity` parse as non-finite floats and are written back with those exact spellings while finite floats keep `repr` semantics through `py_float_repr`; the writer emits `json.dumps(s, indent=2, sort_keys=True)` plus one LF with `ensure_ascii=True` escaping (short forms and `\uXXXX` for 0x00-0x1f, `\uXXXX` for 0x7f and every char above, astral chars as surrogate pairs); integers saturate at i64 as everywhere in the port, so a bignum in a settings file is the one divergence the differential protocol cannot carry - pinned by rust tests instead; duplicate keys are last-wins like a python dict; a lone-surrogate `\u` escape (unrepresentable in a rust String) maps to U+FFFD, recorded - python keeps the lone surrogate; the read path applies python's universal-newline translation (CRLF and lone CR to LF) for both the load parse and the `save_settings` skip-compare, so a CRLF file equal to the LF render is skipped exactly like python, and the loader never writes; a settings file whose JSON is not an object is where python raises outside its `try` - the port carries those as typed error branches and the harness compares port-domain shape tokens (`unreadable`, `type_error`, `attribute_error`, `not_utf8`) because payloads are shape-gated per the message rule above; `not_utf8` is the invalid-UTF-8 case where python raises `UnicodeDecodeError` in the save compare, while every other read failure falls through to the write like python's `except OSError`.
