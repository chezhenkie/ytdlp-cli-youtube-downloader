## 1. Problem, goals, non-goals

Problem: downloading a youtube video with yt-dlp means remembering flags. Users want to paste a url, press enter, and have a download run with sensible saved defaults, changeable without flags.

Goal: a text-menu CLI that owns the menu, the launchers, the defaults and the process plumbing, and delegates every byte of downloading to yt-dlp. Everyday use is: start, paste url, done. Non-affiliation statement is published verbatim in README.md line 1.

Non-goal: this project is not a download engine, a youtube client, or affiliated with or endorsed by the yt-dlp project (README.md line 1). Thumbnail and metadata options were deliberately dropped (CHANGELOG v1.2 "drop the thumbnail and metadata options"), which also removed the last ffprobe consumers; the product tree has no ffprobe (CHANGELOG v1.2 "delete ffprobe.exe"). Through v2.0.4 no macOS ffmpeg was shipped or fetchable: no free static macOS build was published by the original providers (gyan.dev is Windows only, BtbN ships Windows and Linux), so macOS got install instructions. v2.1.0 closes that gap (owner call 2026-10-17g): the macos source is the shaka-project static build and the macos portable bundle ships (owner call 2026-10-17h: portable-only - the lean mac bundle was pulled; `exec/ffmpeg.rs::ffmpeg_source`; THIRD-PARTY-NOTICES.md).

## 2. Functional requirements

FR-1 Quick download. When a url (any text containing an http(s) substring, cleaned of surrounding punctuation by `clean_url`, args.rs) is entered at the quick-arg path or the main prompt, the system downloads it with saved defaults, per `do_download` (exec.rs). Verified by selftest checks on clean_url and argv building.

FR-2 Menu surface. Thirteen rows numbered 1 to 13 in one always-visible box (WIDTH 64; `menu_items`, ui.rs): 1 video/audio, 2 format container, 3 video resolution, 4 audio format, 5 output folder, 6 filename template, 7 subtitles, 8 playlist on/off, 9 add multiple youtube urls, 10 reset defaults, 11 update yt-dlp + cli, 12 auto update, 13 quit. Above row 1, in the place of the former blank top row, the box paints the FR-17 quick-paste row (fixed text, no value column). Values render per current settings; audio-only greys out container and resolution with "audio only mode has no container" / "...no resolution" refusals (menu.rs `act`). Unknown non-url input prints "pick 1-13 or paste a url".

FR-3 Settings persistence. Every menu change writes config/settings.json immediately, LF line endings, written through a tmp file plus an atomic replace (`save_settings`, config.rs; the replace primitive is pyfs.rs), and skipped entirely when the serialized bytes are unchanged. Unknown keys in the json are ignored on load (`load_settings`, config.rs). Quick-run overrides never persist: the url dispatch path (main.rs) runs `do_download` directly and never calls save_settings.

FR-4 Menu input protocol. The prompt takes a url, a number, or 0 (FR-17; a bare 0 acts on the keypress on a real tty, no enter); "q", "quit", "exit" also quit (menu.rs). Escape at the main prompt wipes results or is a no-op and never exits; EOF and Ctrl+C exit code 0. Escape inside any submenu raises GoBack and repaints the menu once (`main_menu`, menu.rs). Every submenu message holds on screen behind an unlabelled `hold()` read so the repaint cannot erase it (tty.rs; pinned per call site by the selftest).

FR-5 Entry reader. A tty-aware line reader over LineEdit (tty.rs): the CRT key pair on windows, termios+raw on posix, plain line reads when piped (`read_esc`). Up/down arrows recall submitted urls and menu numbers, newest first, down past the newest restores the half-typed draft, left/right and function keys put nothing into the line (LineEdit, history capped at 100).

FR-6 Output folder. Saved output_dir wins verbatim; else auto-resolve: windows registry Shell Folders Desktop then the Downloads GUID, else XDG user-dirs, then home Desktop then home Downloads, each gated on existing (`auto_outdir_lookup`/`resolve_outdir`, resolve.rs); last resort "downloads" at the project root. Menu item 5 offers the native folder dialog first (SHBrowseForFolderW on windows; the zenity/kdialog shell-out on posix), typed path as fallback (menu.rs `folder_dialog`).

FR-7 Download run. When a url is dispatched: scheme gate, then yt-dlp resolution (saved yt_dlp_path, then ROOT/bin, then PATH; `find_yt_dlp`, resolve.rs), then one grouped preflight dot stage that freezes "ready - yt-dlp v<version>, ffmpeg found" or the no-ffmpeg variant. The run spawns yt-dlp with stdout/stderr piped, two pump threads, and an escape-only KeyWatch (`run_download`, exec.rs). No input is accepted while a download runs; the only interruption is escape. All yt-dlp intermediates (part files, per-chunk fragment files, resume markers, pre-merge files) go to the download work folder inside the output folder; every run end removes that folder (FR-11).

FR-8 Format logic. `build_args(s, url, ffdir)` with ffdir explicit (args.rs): audio only with ffmpeg: "-f bestaudio/best -x --audio-format <fmt> --audio-quality 0"; audio only without: "-f bestaudio"; video no audio: "bv*[height<=N]" (bare "bv*" for best); video with ffmpeg: "bv*[height<=N]+ba/b" (bare for best) plus "--merge-output-format <container>" unless container is best; video without ffmpeg: "-f b", single best file. Always: --retries 5, --newline, -o template, -P home:<outdir> and -P temp:<outdir>/.ytdlp-tmp unless the template is absolute, playlist block (--playlist-items 1-<n> when capped, else --no-playlist), --js-runtimes node only when node is on PATH, --ffmpeg-location when ffdir exists. The temp path is the download work folder (TEMP_DIR_NAME .ytdlp-tmp inside the output folder, `temp_dir`, exec.rs): yt-dlp writes every per-chunk fragment file, .part file, .ytdl resume marker and pre-merge file there (pinned source: downloader/fragment.py `_download_fragment`/`_append_fragment` in resources/ytdlp-master.zip), so the output folder shows finished files only and the final move is a same-volume rename; owner decision 2026-10-14 after the measured flicker: 396 fragment create/delete events in the output folder for one 10-minute HLS download, 1 final-file event with the work folder. Exact selector strings are pinned by selftest. Without ffmpeg the CLI says so and degrades rather than failing (stage variants, exec.rs).

FR-9 Subtitles pass. Subtitles run only after a successful video download, as a separate best-effort yt-dlp pass with --skip-download --write-subs --write-auto-subs --sub-langs <patterns> --no-playlist --newline --convert-subs srt (vtt without ffmpeg) (`build_sub_args`, args.rs; `do_download`, exec.rs). Rationale pinned in code: a rate-limited subtitle api (HTTP 429) must never block the video (args.rs comment). Language input maps to patterns so en matches en, en-GB, en-US and en-orig (`parse_lang_input`, args.rs); the 191-code IANA BCP 47 reference set (plus grandfathered in/iw/ji/mo/sh and fil, KNOWN_LANG_CODES, args.rs) validates shaped tokens but never gates: well-formed unknown codes are kept with a note, malformed ones are dropped with a note, and nothing valid left keeps the old value. Verdict lines build through sub_success_lines(codes) and sub_fail_lines(err) so the parse-miss notes of IF-4 are testable outside a download run.

FR-10 Stage lines. Every progress line rewrites after "\r\x1b[K" so a shorter value never leaves a tail (Stage, tty.rs). Preflight, ffmpeg offer and subtitle stages use the amber dot stage (`dot_stage`, tty.rs). The download stage picks one of eight random animations per run (comet, pulse, orbit, scanner, twinkle, eq, fill, bounce; `pick_spinner`, term.rs; adapted from scripts-tools/spinner-demo.py) and keeps spinning beside yt-dlp's own progress numbers. Progress colors: percent amber 214, size mint 121, speed light blue 117, ETA purple 176, plain words grey 250 (`color_progress`, term.rs); numbers are width-stable: one decimal truncated (`one_dec_num`) and speed zero-padded to the same ten characters yt-dlp pads (`pad_speed`). A write lock serializes spinner threads against freezes (tty.rs). Verdict freezes: success "downloading - finished" plus a file line; failure "downloading - failed (rc=...): <full yt-dlp error line>" untruncated (`fail_sentence`, exec.rs); escape stop "downloading - stopped by escape[, cleaned <n> partial file(s)]" (exec.rs).

FR-11 Escape interruption. Escape during a run kills the whole process tree (taskkill /F /T on windows, killpg SIGKILL on posix; exec/run.rs), deletes fresh *.part* and *.ytdl files from the work folder (`clean_partials`, exec.rs), and returns rc 130 which breaks a batch entirely (menu.rs `run_batch`).

WORK FOLDER RULE (owner-decided 2026-10-16c, during the OQ-N2 console pass: the owner watched .ytdlp-tmp survive a Ctrl+C and called it - nothing in there has value). Every native run end removes the work folder with whatever it holds - success, failure, escape (keeping the clean-then-remove shape and rc 130) and Ctrl+C, all through one force-remove (`drop_temp_dir_force`, exec.rs) at `do_download`'s run ends. This supersedes NFR-3's "removed whenever it ends empty" and "partials with resume value are never deleted silently" for every run: no run state survives, and the named consequence is that the 429-subtitle keep-for-retry across runs does not exist - a retry re-fetches. `drop_temp_dir` itself keeps the empty-only semantics with its function-level selftest checks unchanged - only the call sites changed.

FR-12 Batch downloads. Menu item 9 collects urls one per line with the menu repainting above the input; entries with no http link stay in the list marked "error in url" and are skipped at run time; downloads run strictly sequential in paste order; escape inside any run stops that run and the rest of the batch (`multi_url`, `run_batch`, menu.rs).

FR-13 Updaters. Menu item 11 runs `update_all` (update.rs): yt-dlp updates itself via "<binary> -U" with a pre and post `probe_version` (`update_yt_dlp`, update.rs), then the CLI self-updates from the GitHub releases API, fetched in one GET so version and digest cannot disagree (`fetch_cli`, update.rs):
  - The newest release tag, that tag's bare-binary asset for the running platform (`ytdlp-native-linux-x86_64`, `ytdlp-native-windows-x86_64.exe`, published alongside the bundles; macOS publishes none - owner call 2026-10-17h, the mac line is the portable bundle only, so the fetch is the missing-asset refusal there) and the sha256 digest published per asset in the same response. A leading v is stripped from the tag before the version comparison; a missing platform asset or a missing digest is a refusal, not a download. The property being preserved is that version and binding digest travel together.
  - The validity gate is `<new> --selftest` once before anything is touched. A binary that cannot pass its own checks is never installed.
  - Install by renaming the running binary to `.old` and placing the new one at its path (`install_cli`, update.rs). This is required because a running Windows exe cannot be overwritten and a running ELF yields ETXTBSY on rename; rename-then-place is legal on both and leaves the running process on its own inode. The `.old` file is removed on the next successful start (`remove_previous_image`, update.rs).
  - All of it stays behind the existing y/n prompt, and no existing file is touched until the prompt is answered yes.
  Rationale: the digest-plus-selftest gate is strictly stronger than parsing a source file, and it is the only formulation that works on a compiled artifact. TRIGGER RULE (owner-pinned 2026-10-14, doc only - no behavior change): the check lives at exactly one call site, the top of `main_menu`, and runs only there and only when stdin is a real console (tty). Quick mode (a url passed as argument), --check, --selftest, CI, and every piped or detached run skip it entirely: no network contact, no settings stamp. There is no resident program and no timer during a session - the check is one-shot at menu open, throttled by the stamp. Consequence for the user: auto-update can only ever be offered while you sit at a console menu you started yourself; if updates seem to not happen, the answer is that no interactive menu was opened - run the program and the check runs with it.
  Menu item 12 toggles the daily auto-update check, which stamps settings auto_update_last_check, throttles to one check per 86400 s, only prints what is newer, and asks y/n (enter = no) before touching anything (`auto_update_check`, update.rs).

FR-14 ffmpeg fetch offer. On an os with no ffmpeg and a human on the line (stdin tty), the CLI offers the published build and installs only after reading the provider's published digest, downloading to a temp path, verifying sha256, lifting the binary from the archive, and probing -version success (retried 3 times), then replacing into bin/ with mode 0755 on posix; checksum mismatch or unrunnable binary changes nothing (`install_ffmpeg`, `offer_ffmpeg`, exec/ffmpeg.rs; "checksum before install" order documented in the code comment there and in RELEASE-NOTES.md).

WINDOWS SOURCE RULE (owner-decided 2026-10-16c, during the OQ-N2 console pass: a live offer download measured ~300 KB/s from gyan.dev on the owner's line). The native Windows offer fetches the BtbN/FFmpeg-Builds win64 GPL build - the same provider the Linux side uses. The digest-first gate is unchanged: the provider's published `checksums.sha256` is read first, the archive is verified against it, extracted and probed exactly as before; the source is `ffmpeg-n9.0-latest-win64-gpl-9.0.zip` on the moving `latest` tag (safe because the digest is read fresh on every run, so the tag moving cannot go stale). Verified 2026-10-16: 193963209 bytes, sha256 177bec2e8c3397c5e9739901993dadc1cad0954de97d2604a2704c8531a59e32, member `ffmpeg-n9.0-latest-win64-gpl-9.0/bin/ffmpeg.exe` (the same versioned-folder layout the extractor already matches). The linux offer keeps the BtbN tar.xz. The selftest check `windows ffmpeg source is BtbN` pins the native source. The portable bundles' shipped ffmpeg payload pins are NOT touched by this rule: v2.0.0 and v2.0.1 shipped the pinned gyan build, and a future release decides its own payload pins.

MACOS SOURCE RULE (owner-decided 2026-10-17g; amended 2026-10-17h when the mac line became portable-only). macOS joins the offer whenever ffmpeg is missing: no macOS machine has ffmpeg by default, and without one yt-dlp silently falls back to the single pre-merged file (on YouTube typically 360p) with no mp3 and no remux - a degraded default, not an acceptable one, so the offer exists on all three platforms. The source is the shaka-project/static-ffmpeg-binaries release `n8.1.2-1`, asset `ffmpeg-osx-arm64` - a public repository with contributors, built from source in its own GitHub Actions workflow (x264/x265/lame -> the GPL line, same as the other two platforms), license texts shipped the same way. This provider publishes no checksum file, so the digest is the GitHub release API object's per-asset `digest` field, read first exactly like the checksums-file read (pinned tag: the artifact cannot move under the digest). The asset is the binary itself (how "raw"): the download is chmod 0755, probed, then renamed into `bin/ffmpeg` - no archive step. Verified 2026-10-17: 34074040 bytes, sha256 e7b9fcd97f95f333512d6e8b8ac24d9dbc08f189f36047695499bd7b57214b22 (matches the API digest). arm64 only - that is the CI runner and the payload. The selftest check `macos ffmpeg source is shaka-project` pins the native source; the differ projects it to python's `no ffmpeg download for macos` (conformance map, section 10).

FR-15 Diagnostics. --check prints platform, project root, resolved yt-dlp binary and version, ffmpeg dir or MISSING, output folder and settings file (`show_check`, resolve.rs). --update is the non-interactive form of item 11 (main.rs).

FR-16 Windows file metadata (owner call 2026-10-16; FileDescription shortened to "ytdlp" by owner call 2026-10-17g - the long descriptive text propagated into every place Windows shows an app name, with no room for it). The shipped `ytdlp.exe` carries a complete PE version resource so Explorer's Properties dialog shows the product identity without opening anything: FileDescription "ytdlp", ProductName "yt-dlp cli", FileVersion and ProductVersion tied to the product version (v2.0.0 for the first native release), CompanyName "chezhenkie", LegalCopyright "MIT License", InternalName and OriginalFilename "ytdlp", Comments "https://github.com/chezhenkie/ytdlp-cli-youtube-downloader".
Verification: the CI windows job asserts the built exe's VersionInfo fields, G10 repeats the assertion on the extracted bundle, and the owner checks the Details tab in the OQ-N2 console pass (closed 2026-10-16c).

FR-17 Quick paste row (owner call 2026-10-16; the v2.0.2 feature). The menu box opens with a row 0 above row 1, where the former blank top row stood: label "press zero '0' to paste link and start direct download", no value column, painted a little darker than the box amber (256-color 208; the key color stays 214). Pressing 0 fires at once - on a real tty the bare 0 keypress acts on the empty input line, no enter (the main prompt's `read_line_quick0` read; scripted readers and piped stdin keep the 0-then-enter line path, the trait default). The action reads the system clipboard (windows: the Win32 clipboard, CF_UNICODETEXT text via windows-sys; posix: the first of `wl-paste`, `xclip`, `xsel`, `pbpaste` that is on PATH and answers), takes the first http(s) link from it with clean_url semantics, and starts the download with saved defaults exactly like a pasted url plus enter - the screen repaints to the menu with the run's stage and verdict lines under it (the results screen; escape wipes it). A clipboard with no link, or no clipboard tool: one amber line "no link on the clipboard", a hold read, and a menu repaint; nothing else happens. A 0 typed later inside a line stays an ordinary character; submenu and hold reads are untouched. The clipboard read enters the menu world as a seam (`menu::World`), so tests script it; the row bytes, both flows and the tty quick-key rule are pinned by the crate's unit tests. The differential harness and the session differ project the row to the `{menu-quick-row}` token on both sides (the reference paints its blank box row there), so the row's exact bytes stay outside the differential by design.

## 3. Non-functional requirements

NFR-1 No system runtime. The published artifact runs on a machine with nothing installed beyond its own bundle: no interpreter, no package manager, no redistributable, no toolchain. One statically self-contained binary per platform. The Microsoft Visual C++ runtime is not acceptable either: `x86_64-pc-windows-msvc` links that runtime dynamically by default and would require vcruntime140.dll on the host, so `.cargo/config.toml` sets `-C target-feature=+crt-static` for that target. Verified: `rustc --print cfg --target x86_64-pc-windows-msvc` reports no crt-static by default and reports `target_feature="crt-static"` with the flag. Omitting it builds cleanly and fails only at the user's machine, so gate G1 asserts the built exe's PE import table contains no vcruntime*.dll and no msvcp*.dll, and gate G10 repeats the assertion against the extracted bundle. Build-time dependencies are a separate concern from end-user dependencies and are recorded in section 4; crates are build-time only and ship no runtime requirement.

NFR-2 Machine-agnostic: no hardcoded paths anywhere; bin discovery is settings override, then bin/, then PATH; output resolves per os (FR-6, FR-7). Windows, linux and macOS run in CI (.github/workflows/rust.yml); the linux launcher must survive sh/dash via `$0`, not `${BASH_SOURCE[0]}` (CHANGELOG v1.3 "first public release").

NFR-3 Process hygiene: `run_download`'s threads are daemonized, escape kills the tree and cleans partials, the ffmpeg installer removes its temp dir on every path, and repeated runs leave no leaked processes, stale files or lingering threads (exec.rs, exec/ffmpeg.rs; `cli/tests/exec_100_runs.rs` runs 100 downloads against the stand-in and asserts no lingering process, identical argv, no surviving work folder and no file-descriptor growth). The download work folder never survives a run (FR-11): every run end removes it with contents, partials included.

NFR-4 Testability: every requirement has at least one executable check, and all checks are offline. The packaged suite is `--selftest` (selftest/): 177 checks covering argv building, format branches, playlist/sub guards, color and width rules, spinner shapes, render helpers, outdir resolution, download work folder argv and cleanup (temp path, fresh-partial removal, empty-folder removal), fail_sentence, menu rows, batch order and escape stop, language parsing and layout, hold call sites, checksum parsers, install_cli refusals, extract_member fixtures, the ffmpeg-9 probe shim, the audit regressions (settings boundary coercion, the 6 s auto-check timeout, probe and outdir memos, the single save point, column-width menu truncation), and the parse-miss verdict helpers. Two acceptance rules bind the checks:
  - Differential, not reimplemented. The native checks must assert the same expected values the reference asserts for the same inputs; the check stream is compared one-to-one by `rust-src/tools/selftest_compare.py`. A check that merely re-expresses the implementation's own output proves nothing and is not accepted.
  - The instrument is proven before it judges. The differential harness (`rust-src/tools/harness.py`) must pass against known reference answers before it is used to evaluate native code; it drives function-level vectors, and `rust-src/tools/session_diff.py` drives binary-level piped and pty golden transcripts. `run-all` is the differential gate: 69 functions / 978 records / 0 mismatches. CI (rust.yml) runs the same gate plus fmt, clippy with warnings denied and cargo tests on windows, ubuntu and macos; `bundles.yml` (workflow_dispatch) assembles the release bundles. Neither workflow contacts the network in a test.

NFR-5 Privileged controls. Authentication and authorization do not apply (single-user local tool). Enforced locally: input validation at the url scheme gate (exec.rs `do_download`) and the CLI parser's choice validation (cli_args.rs); secrets: settings.json ships no machine paths, repo carries no binaries (bin/ and releases/ gitignored, .gitignore); integrity: every downloaded binary is digest-verified before installation (FR-13, FR-14); logging: stage lines are the whole observable log and stdout/stderr tails keep the last 6 error lines (exec.rs); retention: only user-chosen paths in the user's own settings.

NFR-6 ASCII-only source and console safety: `ascii_safe` maps unicode punctuation and encodes the rest with replace so windows cp1252 cannot crash output (term.rs).

NFR-7 Outside a tty the CLI renders plain: no colors, stages skip the spinner thread and only the final line prints (term.rs `c()`, tty.rs `Stage`).

NFR-8 Licensing compliance as a design property: MIT CLI (LICENSE), Unlicense yt-dlp, GPL-2.0-or-later ffmpeg shipped only in portable bundles with GPL-2.0.txt and GPL-3.0.txt inside and THIRD-PARTY-NOTICES.md naming the exact archive and digest per platform (THIRD-PARTY-NOTICES.md lines 8-46); nothing in the bundle restricts GPL rights for ffmpeg (lines 47-51). Binaries are never in git.
