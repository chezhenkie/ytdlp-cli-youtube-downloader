## 1. Problem, goals, non-goals

Problem: downloading a youtube video with yt-dlp means remembering flags. Users want to paste a url, press enter, and have a download run with sensible saved defaults, changeable without flags.

Goal: a text-menu CLI that owns the menu, the launchers, the defaults and the process plumbing, and delegates every byte of downloading to yt-dlp. Everyday use is: start, paste url, done. Non-affiliation statement is published verbatim in README.md line 1.

Non-goal: this project is not a download engine, a youtube client, or affiliated with or endorsed by the yt-dlp project (README.md line 1). Thumbnail and metadata options were deliberately dropped (CHANGELOG v1.2 "drop the thumbnail and metadata options"), which also removed the last ffprobe consumers; the product tree has no ffprobe (CHANGELOG v1.2 "delete ffprobe.exe"). No macOS ffmpeg bundle: no free static macOS build is published by the pinned providers (gyan.dev is Windows only, BtbN ships
Windows and Linux) and no free static macOS build exists
(THIRD-PARTY-NOTICES.md lines 37-38; ytdlp.py L380-L386), so macOS gets install instructions (install_ffmpeg L1455-L1459, offer_ffmpeg L1534-L1537).

## 2. Functional requirements

FR-1 Quick download. When a url (any text containing an http(s) substring, cleaned of surrounding punctuation by clean_url, ytdlp.py L692-L696, L316) is entered at the quick-arg path or the main prompt, the system downloads it with saved defaults, per do_download L1562-L1639. Verified by selftest checks on clean_url and argv building (ytdlp.py L2640-L2642, L2449-L2589).

FR-2 Menu surface. Thirteen rows numbered 1 to 13 in one always-visible box (WIDTH 64, ytdlp.py L34; menu_items L1892-L1930): 1 video/audio, 2 format container, 3 video resolution, 4 audio format, 5 output folder, 6 filename template, 7 subtitles, 8 playlist on/off, 9 add multiple youtube urls, 10 reset defaults, 11 update yt-dlp + cli, 12 auto update, 13 quit. Values render per current settings; audio-only greys out container and resolution with "audio only mode has no container" / "...no
resolution" refusals (L2225-L2234). Unknown non-url input prints "pick 1-13 or paste a url" (L2348-L2349).

FR-3 Settings persistence. Every menu change writes app-python/config/settings.json immediately, LF line endings, written through a tmp file and os.replace, and skipped entirely when the serialized bytes are unchanged (save_settings L483-L499). Unknown keys in the json are ignored on load (load_settings L473-L475). Quick-run overrides never persist: the url dispatch path (L3268-L3269) runs do_download directly and never calls save_settings.

FR-4 Menu input protocol. The prompt takes a url or a number; "q", "quit", "exit" also quit (L2344); escape at the main prompt wipes results or is a no-op and never exits; EOF and Ctrl+C exit code 0 (L1974-L1982). Escape inside any submenu raises GoBack and repaints the menu once (GoBack L123-L125, handler L1996-L1999). Every submenu message holds on screen behind an unlabelled hold() read so the repaint cannot erase it (hold L1649-L1656; pinned per call site by selftest L2945-L3006).

FR-5 Entry reader. A tty-aware line reader over LineEdit: msvcrt on windows, termios+raw on posix, plain input() when piped (read_esc L233-L314). Up/down arrows recall submitted urls and menu numbers, newest first, down past the newest restores the half-typed draft, left/right and function keys put nothing into the line (LineEdit L131-L187, history capped at 100, HISTORY L127-L128).

FR-6 Output folder. Saved output_dir wins verbatim; else auto-resolve: windows registry Shell Folders Desktop then the Downloads GUID, else XDG user-dirs, then home Desktop then home Downloads, each gated on existing (auto_outdir L544-L576, resolve_outdir L579-L588); last resort "downloads" at the project root. Menu item 5 offers the native folder dialog first (SHBrowseForFolderW via ctypes L2019-L2047, tkinter/zenity/kdialog L2050-L2076), typed path as fallback (L2237-L2247).

FR-7 Download run. When a url is dispatched: scheme gate, then yt-dlp resolution (saved yt_dlp_path, then ROOT/bin, then PATH, L618-L629), then one grouped preflight dot stage that freezes "ready - yt-dlp v<version>, ffmpeg found" or the no-ffmpeg variant (L1574-L1588). The run spawns yt-dlp with stdout/stderr piped, two daemon pump threads, and an escape-only KeyWatch (run_download L1238-L1308). No input is accepted while a download runs; the only interruption is escape. All yt-dlp
intermediates (part files, per-chunk fragment files, resume markers, pre-merge files) go to the download work folder inside the output folder; the folder is removed when it ends empty (FR-8, FR-11) - natively it never survives a run at all (FR-11 amendment 2026-10-16c).

FR-8 Format logic. build_args(s, url, ffdir) with ffdir explicit (L762-L808): audio only with ffmpeg: "-f bestaudio/best -x --audio-format <fmt> --audio-quality 0"; audio only without: "-f bestaudio"; video no audio: "bv*[height<=N]" (bare "bv*" for best); video with ffmpeg: "bv*[height<=N]+ba/b" (bare for best) plus "--merge-output-format <container>" unless container is best; video without ffmpeg: "-f b", single best file. Always: --retries 5, --newline, -o template, -P home:<outdir> and -P
temp:<outdir>/.ytdlp-tmp unless the template is absolute, playlist block (--playlist-items 1-<n> when capped, else --no-playlist), --js-runtimes node only when node is on PATH, --ffmpeg-location when ffdir exists. The temp path is the download work folder (TEMP_DIR_NAME .ytdlp-tmp inside the output folder, temp_dir L594-L603): yt-dlp writes every per-chunk fragment file, .part file, .ytdl resume marker and pre-merge file there (pinned source: downloader/fragment.py
_download_fragment/_append_fragment in resources/ytdlp-master.zip), so the output folder shows finished files only and the final move is a same-volume rename (movefilesafterdownload.py L50); owner decision 2026-10-14 after the measured flicker: 396 fragment create/delete events in the output folder for one 10-minute HLS download, 1 final-file event with the work folder. Exact selector strings are pinned by selftest (L2449-L2589). Without ffmpeg the CLI says so and degrades rather than failing
(stage variants L1583-L1587).

FR-9 Subtitles pass. Subtitles run only after a successful video download, as a separate best-effort yt-dlp pass with --skip-download --write-subs --write-auto-subs --sub-langs <patterns> --no-playlist --newline --convert-subs srt (vtt without ffmpeg), (build_sub_args L811-L824, do_download L1623-L1637). Rationale pinned in code: a rate-limited subtitle api (HTTP 429) must never block the video (L765-L766, L812). Language input maps to patterns so en matches en, en-GB, en-US and en-orig
(sub_lang_patterns L707-L719); the 191-code IANA BCP 47 reference set (plus grandfathered in/iw/ji/mo/sh and fil, KNOWN_LANG_CODES L349-L371) validates shaped tokens but never gates: well-formed unknown codes are kept with a note, malformed ones are dropped with a note, and nothing valid left keeps the old value (parse_lang_input L722-L744). Verdict lines build through sub_success_lines(codes) and sub_fail_lines(err) so the parse-miss notes of IF-4 are testable outside a download run.

FR-10 Stage lines. Every progress line rewrites after "\r\x1b[K" so a shorter value never leaves a tail (Stage L1035-L1090). Preflight, ffmpeg offer and subtitle stages use the amber dot stage (dot_stage L843-L849). The download stage picks one of eight random animations per run (comet, pulse, orbit, scanner, twinkle, eq, fill, bounce; pick_spinner L1010-L1012, SPINNERS L997-L1007, ported from scripts-tools/spinner-demo.py, comment L852-L854) and keeps spinning beside yt-dlp's own progress
numbers. Progress colors: percent amber 214, size mint 121, speed light blue 117, ETA purple 176, plain words grey 250 (color_progress L97-L120); numbers are width-stable: one decimal truncated (one_dec_num L72-L79) and speed zero-padded to the same ten characters yt-dlp pads (pad_speed L82-L94). A write lock serializes spinner threads against freezes (L1056, L1083-L1086). Verdict freezes: success "downloading - finished" plus a file line; failure "downloading - failed (rc=...): <full yt-dlp
error line>" untruncated (fail_sentence L1311-L1316); escape stop "downloading - stopped by escape[, cleaned <n> partial file(s)]" (L1599-L1607).

FR-11 Escape interruption. Escape during a run kills the whole process tree (taskkill /F /T on windows, killpg SIGKILL on posix, _kill_tree L1223-L1235), deletes fresh *.part* and *.ytdl files from the work folder (clean_partials L1163-L1177, called on escape at L1600, mtime after run start with 5 s slack; drop_temp_dir L606-L612 removes the folder when it ends empty), and returns rc 130 which breaks a batch entirely (L1599-L1607, L1743-L1744).

WORK FOLDER, NATIVE AMENDMENT (owner-decided 2026-10-16c, during the OQ-N2 console pass: the owner watched .ytdlp-tmp survive a Ctrl+C and called it - nothing in there has value). Native runs never leave the work folder behind: every run end removes it with whatever it holds - success, failure, escape (keeping the clean-then-remove shape and rc 130) and Ctrl+C, all through one force-remove at the do_download run ends. This supersedes, for the native line only, NFR-3's
"removed whenever it ends empty" and "partials with resume value are never deleted silently": no run state survives, and the named consequence is that python's 429-subtitle keep-for-retry across runs does not apply natively (a retry re-fetches). The frozen python line keeps its resume-keeping behavior, and `drop_temp_dir` itself keeps python's empty-only semantics with its function-level selftest checks unchanged - only the native call sites change.

FR-12 Batch downloads. Menu item 9 collects urls one per line with the menu repainting above the input; entries with no http link stay in the list marked "error in url" and are skipped at run time; downloads run strictly sequential in paste order; escape inside any run stops that run and the rest of the batch (multi_url L1749-L1772, run_batch L1718-L1746).

FR-13 Updaters. Menu item 11 runs update_all: yt-dlp updates itself via "<binary> -U" with a pre and post probe_version (update_yt_dlp L2079-L2103), then the CLI self-updates from the raw main-branch source file, fetched in one GET so version and bytes cannot disagree (fetch_cli L2120-L2128, comment L398-L399), gated by compile() and installed via ".new" file plus os.replace, refusing zipapp or frozen installs (install_cli L2131-L2155). Menu item 12 toggles the daily auto-update check, which
runs at menu start, stamps settings auto_update_last_check, throttles to one check per 86400 s, only prints what is newer, and asks y/n (enter = no) before touching anything (auto_update_check L2158-L2204, L1971).

SELF-UPDATE, NATIVE IMPLEMENTATION (owner-decided 2026-10-14; the one place where "same as python" is deliberately not literal). A running executable cannot be overwritten on either platform, and `compile()` has no native analogue, so the native install replaces the file and the validity gate is replaced with a stronger one:
  - Resolve the newest release tag, download that tag's asset for the running platform, and verify it against the digest published with it.
    The property being preserved is that version and binding digest travel together. Decided 2026-10-15: one GET of the GitHub releases API
    returns the newest tag plus a sha256 digest per asset; the running platform maps to its bare-binary asset (ytdlp-native-linux-x86_64,
    ytdlp-native-windows-x86_64.exe, published alongside the bundles); a leading v is stripped from the tag before the version comparison;
    a missing platform asset or a missing digest is a refusal, not a download.
  - Run `<new> --selftest` once before anything is touched. A binary that cannot pass its own checks is never installed.
  - Install by renaming the running binary to `.old` and placing the new one at its path. This is required because a running Windows exe cannot be overwritten and a running ELF yields ETXTBSY on rename; rename-then-place is legal on both and leaves the running process on its own inode. The `.old` file is removed on the next successful start.
  - All of it stays behind the existing y/n prompt, and no existing file is touched until the prompt is answered yes.
Rationale: the digest-plus-selftest gate is strictly stronger than parse-the-source, and it is the only formulation that works on a compiled artifact. TRIGGER RULE (owner-pinned 2026-10-14, doc only - no behavior change): the check lives at exactly one call site, the top of main_menu, and runs only there and only when stdin is a real console (tty). Quick mode (a url passed as argument), --check, --selftest, CI, and every piped or detached run skip it entirely: no network contact, no settings
stamp. There is no resident program and no timer during a session - the check is one-shot at menu open, throttled by the stamp. Consequence for the user: auto-update can only ever be offered while you sit at a console menu you started yourself; if updates seem to not happen, the answer is that no interactive menu was opened - run the program and the check runs with it.

FR-14 ffmpeg fetch offer. On an os with no ffmpeg and a human on the line (stdin tty), the CLI offers the published build - gyan.dev essentials zip on windows, BtbN/FFmpeg-Builds on linux - and installs only after reading the provider's published digest, downloading to a temp path, verifying sha256, lifting the binary from the archive, and probed -version success (retried 3 times), then os.replace into bin/ with chmod 0o755 on posix; checksum mismatch or unrunnable binary changes nothing
(install_ffmpeg L1446-L1512, offer_ffmpeg L1515-L1559; order rationale L1447-L1453).

FFMPEG OFFER SOURCE, NATIVE IMPLEMENTATION (owner-decided 2026-10-16c, during the OQ-N2 console pass: a live offer download measured ~300 KB/s from gyan.dev on the owner's line). The native Windows offer fetches the BtbN/FFmpeg-Builds win64 GPL build instead - the same provider the Linux side already uses. The property being preserved is the digest-first gate: the provider's published `checksums.sha256` is read first, the archive is verified against it, extracted and probed exactly as before;
the source is `ffmpeg-n9.0-latest-win64-gpl-9.0.zip` on the moving `latest` tag (safe because the digest is read fresh on every run, so the tag moving cannot go stale). Verified 2026-10-16: 193963209 bytes, sha256 177bec2e8c3397c5e9739901993dadc1cad0954de97d2604a2704c8531a59e32, member `ffmpeg-n9.0-latest-win64-gpl-9.0/bin/ffmpeg.exe` (the same versioned-folder layout the extractor already matches). The frozen Python line keeps gyan.dev; this is a recorded native decision like FR-13's, so the
selftest check `windows ffmpeg source is gyan.dev` runs natively as `windows ffmpeg source is BtbN` - the third comparator mapping, with the selftest_compare and session_diff projections extended to match. Check count, order and the record set are unchanged. The portable bundles' shipped ffmpeg payload pins are NOT touched by this amendment: v2.0.0 ships the pinned gyan build, and a future release decides its own payload pins.

FR-15 Diagnostics. --check prints platform, project root, resolved yt-dlp binary and version, ffmpeg dir or MISSING, output folder and settings file (show_check L2355-L2366). --update is the non-interactive form of item 11 (L3254, L3266-L3267).

## 3. Non-functional requirements

NFR-1 No system runtime. The published artifact must run on a machine with nothing installed beyond its own bundle: no interpreter, no package manager, no redistributable, no toolchain. Two implementations satisfy this differently.
  - Python (shipped through v1.5.0): stdlib only, Python 3, no pip installs (docstring L8); launchers name python/python3 from PATH; CI pins 3.12, workflow L21-L23. Python 3 on PATH is a stated prerequisite of the bundle, documented in README "Requirements".
- Native (`app-rust/`, planned): one statically self-contained binary per platform. No dependency is acceptable at the user's end, including the Microsoft Visual C++ runtime. `x86_64-pc-windows-msvc` links that runtime dynamically by default and would require vcruntime140.dll on the host, so `.cargo/config.toml` sets `-C target-feature=+crt-static` for that target. Verified: `rustc --print cfg --target x86_64-pc-windows-msvc` reports no crt-static by default and reports
`target_feature="crt-static"` with the flag. Omitting it builds cleanly and fails only at the user's machine, so gate G1 asserts the built exe's PE import table contains no vcruntime*.dll and no msvcp*.dll, and gate G10 repeats the assertion against the extracted bundle.
  Build-time dependencies are a separate concern from end-user dependencies and are recorded in section 4; crates are build-time only and ship no runtime requirement.
NFR-2 Machine-agnostic: no hardcoded paths anywhere; bin discovery is settings override, then bin/, then PATH; output resolves per os (FR-6, FR-7). Windows, linux and macOS run in CI (workflow L12-L18); the linux launcher must survive sh/dash via $0, not ${BASH_SOURCE[0]} (CHANGELOG v1.3 "first public release").
NFR-3 Process hygiene: run_download's threads are daemonized, escape kills the tree and cleans partials, the ffmpeg installer removes its temp dir on every path (L1511-L1512), and repeated runs leave no leaked processes, stale files or lingering threads (L1180-L1235). The download work folder is removed whenever it ends empty (drop_temp_dir L606-L612); partials with resume value are never deleted silently. NATIVE AMENDMENT 2026-10-16c: the native line removes the work folder
at every run end, contents included (see FR-11) - the keep-for-resume clauses here are python-only.
NFR-4 Testability: every requirement has at least one executable check in every implementation that ships it, and all checks are offline. The Python suite is `--selftest`, 177 checks covering argv building, format branches, playlist/sub guards, color and width rules, spinner shapes, render helpers, outdir resolution, download work folder argv and cleanup (temp path, fresh-partial removal, empty-folder removal), fail_sentence, menu rows, batch order and escape stop, language parsing and layout,
hold call sites, checksum parsers, install_cli refusals, extract_member fixtures, the ffmpeg-9 probe shim, the audit regressions (settings boundary coercion, the 6 s auto-check timeout, probe and outdir memos, the single save point, column-width menu truncation), and the parse-miss verdict helpers (live run 2026-10-14: "177 checks, 0 failed"). The native suite carries a Rust twin for each of those 177 checks with the same expected output; import-table assertions are CI-side (G1). Two acceptance
rules apply to the port:
  - Differential, not reimplemented. The native suite must assert the same expected values as the Python suite for the same inputs. A check that merely re-expresses the implementation's own output proves nothing and is not accepted as a twin.
  - The instrument is proven before it judges. The differential harness must pass against a known answer produced by the Python implementation before it is used to evaluate any native code.
  The native suite runs the same 177 checks by name, order and count (G9 evidence in section 12; the three renamed checks are mapped in the conformance map in section 10); the import-table assertions live in CI (G1) and are not part of the check count. CI runs selftest then --check on all three os (workflow L24-L27).
NFR-5 Privileged controls. Authentication and authorization do not apply (single-user local tool). Enforced locally: input validation at url scheme gate L1563-L1565 and argparse choices L3245-L3247; secrets: settings.json ships no machine paths, repo carries no binaries (bin/ and releases/ gitignored, .gitignore); integrity: every downloaded binary is digest-verified before installation (FR-13, FR-14); logging: stage lines are the whole observable log and stdout/stderr tails keep the last 6
error lines (L1272-L1277); retention: only user-chosen paths in the user's own settings.
NFR-6 ASCII-only source and console safety: ascii_safe maps unicode punctuation and encodes the rest with replace so windows cp1252 cannot crash output (ascii_safe L1093-L1102).
NFR-7 Outside a tty the CLI renders plain: no colors, stages skip the spinner thread and only the final line prints (c() L62-L70, USE_COLOR L44, Stage.start L1058-L1061).
NFR-8 Licensing compliance as a design property: MIT CLI (LICENSE), Unlicense yt-dlp, GPL-2.0-or-later ffmpeg shipped only in portable bundles with GPL-2.0.txt and GPL-3.0.txt inside and THIRD-PARTY-NOTICES.md naming the exact archive and digest per platform (THIRD-PARTY-NOTICES.md lines 8-46); nothing in the bundle restricts GPL rights for ffmpeg (lines 47-51). Binaries are never in git.
