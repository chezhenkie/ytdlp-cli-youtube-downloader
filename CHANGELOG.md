staged download flow, spinner demo
----------------------------------
The download screen was rebuilt around the spinner demo (src/spinner-demo.py, five 4-char candidates): the user picked the dots animation for every non-download stage and the chevron animation for the download itself, capped at three dots and three chevrons, each stage on its own single line with the animation first and a short sentence after it, and yt-dlp's raw output replaced by DEVNULL with only the exit code reported. The sub-second preflight checks (yt-dlp version probe, ffmpeg lookup) are grouped into one animated line, since animating them separately would only flash. Stage lines freeze when their stage ends - a colored "..." or ">>>" prefix plus the final sentence - and are never cleared by the CLI; they disappear only on the next URL, a menu pick, or escape, which repaints the menu. A probe recorded the full frame sequence live: amber dots cycling through ".  ", ".. ", "...", ".. ", ".  " then freezing on "... ready - yt-dlp v2026.08.19, ffmpeg found", then light-blue chevrons cycling ">  ", ">> ", ">>>", ">> ", ">  " and freezing on ">>> downloading - failed, yt-dlp exited rc=1" for a bogus URL, no raw yt-dlp output, and rc=1. newest_since() picks the output file for the final line (verified: a fresh 10-byte probe file is returned, a file aged 600 seconds is ignored) and the size is reported in MB.

The first attempt at this flow was wrong and was corrected the same turn: it cleared the menu off the screen during a download, left a misleading instruction line, and gave no way to stop a run. The rule set the user pinned is: menu always on screen, the input line under the menu, results under the input, and no input at all while a download runs - only escape, which stops yt-dlp and any ffmpeg child and deletes the fresh partial files. run_download therefore polls a raw KeyWatch (msvcrt on windows, cbreak/select on posix) while yt-dlp runs with stdout and stderr sent to DEVNULL, kills the process tree on escape (taskkill /F /T on windows, killpg on posix via start_new_session), and clean_partials removes only fresh *.part* and *.ytdl leftovers. Probes verified: a child process sleeping 30s died 0.3s after the mocked escape, tasklist showed zero orphaned children after kill_tree, a fresh probe partial was deleted while a one-hour-old one survived, and the stop path printed ">>> downloading - stopped by escape, cleaned 1 partial file" with rc=130. main_menu repaints a fresh menu when a URL is entered, keeps the result lines on screen after the run, and clears them on the next url, menu pick, or escape (escape with no results stays a no-op, as pinned earlier).

subtitle 429 fix, progress line, lang patterns (d1b89cf)
---------------------------------------------------------
The user reported that only about one in three downloads succeeded while other apps worked. Reproduced with https://youtu.be/fJxWjwgFljs using the exact CLI argv: yt-dlp printed "[info] Downloading subtitles: en" and then "ERROR: Unable to download video subtitles for 'en': HTTP Error 429: Too Many Requests" and aborted before any video bytes or temp file appeared, so the rate-limited subtitle API was killing the whole run - a run only succeeded when the subtitle fetch was not throttled. Subtitles were therefore removed from the video run entirely and moved into a separate best-effort pass that runs after the video file is on disk (build_sub_args: same -o/-P template, --skip-download, --write-subs --write-auto-subs), so a failing subtitle fetch can no longer block the video; the live settings had "en" only, but YouTube often carries en-GB, en-US and en-orig variants, so the language list is expanded into patterns ("en" becomes "en(-.*)?", "en,nl" becomes "en(-.*)?,nl(-.*)?", existing patterns pass through) instead of a dumb exact match. run_download now pipes yt-dlp's stdout and renders the [download] progress numbers on the stage line itself - "94.8% of 53.55MiB at 10.59MiB/s ETA 00:00", the same figures yt-dlp prints natively - with the chevron prefix frozen while progress flows and the dots animating when no progress is available yet; stderr is captured last-lines-first for one-line failure sentences. When node is on PATH it is passed as --js-runtimes node, which silences the "YouTube extraction without a JS runtime" deprecation warning and restores format coverage (verified: the warning disappears and extraction still succeeds; when node is absent nothing is added). A real end-to-end probe run of the full flow against a second video recorded 146 live progress frames ("0.5% of 101.62MiB at 9.50MiB/s ETA 00:10" through "94.8% of 53.55MiB at 10.59MiB/s ETA 00:00"), then "... done - Making Next Gadget ... mp4 (155.7MB)" and "... subtitles - en-orig, en", rc=0. The same probe also caught a real crash - titles containing a fullwidth vertical bar (U+FF5C) killed the Windows cp1252 console on the done line with UnicodeEncodeError - now handled by ascii_safe, which maps common unicode punctuation and replaces the rest so no yt-dlp text can crash a print.

arrow keys: no garble, up/down recall previous entries (4258616)
--------------------------------------------------------------
The user reported that arrow keys did not bring back previous entries and produced garble at the prompt ("a" followed by M/H/K letters - the right, up, left, right, left, right keys as raw console bytes). Cause: on Windows, getwch returns an extended key as a two-byte sequence, 0xe0 followed by the scan code (H up, K left, M right, P down), and read_esc only special-cased 0x00, so the 0xe0 byte fell through into the input buffer and was echoed as the cp1252 glyph for 0xe0 (a-grave), which is what the user read as "a". KeyWatch.escape_hit already ate ("\x00", "\xe0") pairs - read_esc now does the same. The raw reader was rebuilt around LineEdit, a small buffer with echo, backspace and history: submitted lines (urls and menu numbers alike, non-empty) are recorded in a session list capped at 100 entries, up walks to older entries and down back to newer ones with the half-typed line restored as the draft when passing the newest entry; left/right arrows are consumed with no effect, per the user's choice ("swallowed silently" - no cursor-position editing). On posix terminals, where arrows arrive as ESC [ A / ESC [ B, the lone-escape abort is disambiguated by _esc_more (a short select window) and _csi_final, so escape still exits and the CSI sequences no longer trip the escape branch. Verified by probes driving the real read_esc: the user's exact byte sequence returns None with no 0xe0 leak and a clean echo; up/up then enter returns the oldest preset entry; up then down restores the draft; type+backspace yields "ac"; a 0x00-prefixed key is swallowed; posix ESC [ A recalls the newest entry, ESC [ B returns to the draft, and a lone escape still returns None. Selftest grew to 44 checks, all passing, covering the recall order, the draft restore, history memory and the empty-line skip.

subtitle reason line: classify the full error (84cfa1c)
-----------------------------------------------------
The user checked the live failure and got only the first line ("... subtitles - not fetched (video kept). unable to download subtitles") with no reason line. Root cause found by running the real subtitle pass with the streams captured separately: yt-dlp's stderr holds "ERROR: Unable to download video subtitles for 'en': HTTP Error 429: Too Many Requests" (85 chars) and run_download truncated every error line at WIDTH (64), which left "ERROR: Unable to download video subtitles for 'en': HTTP Error 4" - the "429" was cut off before sub_fail_reason could match it. The earlier probe missed this because it stubbed run_download and fed the classifier the untruncated string; a stubbed probe cannot catch truncation that happens inside the stubbed layer. run_download now returns the error untruncated and the truncation moved to the video failure sentence only, so the subtitle classifier sees the whole line. Verified live: a full piped CLI run against the URL that still 429s printed both lines, "... subtitles - not fetched (video kept). unable to download subtitles" then "... subtitle error - the subtitle api answered 429 too many requests", with the video kept and rc=0. Selftest unchanged at 46 checks.
